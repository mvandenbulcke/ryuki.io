Provider access is brokered through the API alone; the portal never calls provider APIs. The architecture keeps provider credentials behind a secrets resolver (Vault-backed in production; a mock resolver by default) so they are referenced by handle, never embedded in requests or logs.

ryuki-api Rust / Axum / sqlx Control plane API with Entra ID SSO, role-based access, and the governed request lifecycle.
ryuki-engine Rust Domain models, evidence generation, health probes, and provider adapters.

ryuki-validator Rust Self-contained static validation engine (129 modules with a registry-enforced coverage table) for pre-commit and CI guardrails.
ryuki-agent Rust Operator-deployed execution agent. Runs Terraform and Ansible on the operator's own infrastructure and refuses any live apply whose signed grant or plan digest fails verification.
ryuki-runner Rust Process-spawning layer for Terraform and Ansible runs, shared by the agent's dry-run and live paths.
ryuki-protocol Rust Wire contract between the control plane and agents: pure types plus Ed25519 signature primitives, no IO.
PostgreSQL CloudNativePG / Docker Control plane database with schema migrations via sqlx.
Vault HashiCorp Vault Secrets resolver for provider credentials, referenced by handle, never committed or logged. Vault-backed in production; a mock resolver runs by default.
Live Execution

One gated path to live infrastructure

Every domain plans, validates, and records evidence without touching live systems. The single live path runs Terraform and Ansible through an operator-deployed agent, and every step of it is signed.

  1. Plan. An admin dispatches a live plan. The agent runs terraform plan against the real backend and returns scrubbed evidence with a plan digest. Nothing mutates.
  2. Approve. An admin approves that exact plan. The control plane mints a grant signed with its Ed25519 key, binding the request, the plan digest, the approver, and an expiry under 24 hours. Each request gets one live apply, or exactly one per step in an orchestrated run, enforced at the database.
  3. Verify. The agent acts only with RYUKI_AGENT_ALLOW_LIVE=true and a pinned control-plane public key. It re-plans and refuses on any mismatch: bad signature, wrong request, expired grant, or a changed plan digest. Refusals are signed and reported.
  4. Apply. On success the agent applies the saved plan bytes, not a re-plan, so what changes is exactly what was approved. Credentials never reach the control plane.

The dry-run pipeline and the full trust gate are implemented and tested. Pointing an agent at production stays operator-owned: real provider credentials, a durable state backend, and RYUKI_AGENT_ALLOW_LIVE set on purpose.

Quick Start

Running in minutes

Start PostgreSQL, configure the environment, build the workspace, and validate.

shell 
# Start PostgreSQL via Docker Compose
docker compose -f deploy/compose/compose.yaml up -d platform-db

# Copy and configure environment
cp .env.example .env

# Build the full workspace
cargo build --workspace

# Run the test suite
cargo test --workspace

# Execute all validators
cargo run --manifest-path scripts/validator-rs/Cargo.toml -- run-all
